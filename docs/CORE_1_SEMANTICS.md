# Core 1 semantics and trust boundary

This note defines the narrow behavior of the executable Core 1 checker. It does not claim a full language or a soundness proof for an operating system. Program (P) is a strict JSON term `(version=1, actions)`. Host manifest (M) contains `inputs`, `recipients` and `grants`. The host key (K) is provided outside both documents. The checker parses each exactly once and rejects duplicate keys, unknown shapes and non-finite JSON constants.

For a send instruction `(r, x, g)` with known input (x) and recipient (r): `allowed_M(r,x,g)` holds if the host label for (x) is `public`, or if it is `sensitive` and manifest grant (g) equals `(r,x)`. A known send where this predicate fails is a modeled counterexample (`VIOLATED`). An unknown input or recipient, or an opaque call, contributes `UNKNOWN`. Otherwise all sends are conditionally `PROVED`. A VIOLATED case takes precedence over UNKNOWN in a mixed program; a verifier for real arbitrary code would need a more careful treatment of path feasibility and uncertainty.

The modeled transition is `(P,M,K) --analyze--> (verdict, H(P), HMAC_K(M), obligations)`. The simulation recomputes that complete tuple from the supplied documents and key, requires equality with the earlier result and `PROVED`, then returns a list of `(recipient, text)` pairs. **There is no effectful transition to a network or payment system.** Simulation is repeatable: the same approved tuple may be submitted twice. The manifest MAC binds a document under a host-secret key but does not authenticate who supplied its labels, establish a nonforgeable key in a same-process Python adversary, or attest the software implementing the check. HMAC is used rather than an ordinary manifest hash because the manifest may contain low-entropy sensitive text; the key must remain secret. Program digest is unkeyed and must not contain secret input data.

Assumption A1: the host correctly labels inputs. A2: it controls and protects (K) and the manifest. A3: every external effect requested by the agent is forced through a trusted mediator. The implementation checks none of A1–A3. If A1 fails, a mislabeled secret yields PROVED. If A3 fails, independent Python code may send directly. A host-approved result says nothing about intent, purpose, repeated use or third-party model behavior.

The finite test matrix exhausts eight combinations of two labels, two recipients and two grant targets for one known input and one action. This checks conformance of these exact examples to the predicate; it is not an exhaustive proof of Core 1 or of Python. The ordinary Python host API in `comparison/python_api.py` enforces the *same narrow send check* at runtime and is equally bypassable when untrusted Python shares access to other effectful interfaces. Thus the present language core has not established an advantage over an ordinary host API. A compiled, capability-restricted existing-language baseline and real process-level effect confinement remain open.
